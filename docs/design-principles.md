# Принципы проектирования

В исходном диалоге Claude пользователь попросил сравнить «Спутник—Скалар» с современными американскими подходами, затем углубить разбор с опорой на оригинальные труды Кузнецова. Таблица ниже фиксирует архитектурные предложения, появившиеся в ответах Claude, и способы их проверить. Они не маркируются как прямые пользовательские требования, если такая формулировка не подтверждается отдельным сообщением автора.

| Основание / статус | Проектное следствие | Проверка |
|---|---|---|
| Предложение Claude / проектная гипотеза: критерий результата должен отличаться от выполнения списка работ | Цель, критерий, оценка, доказательство и решение о закрытии — разные сущности | Закрыть все задачи без оценки критерия: цель должна остаться непроверенной; затем пройти положительную проверку каждого критерия |
| Предложение Claude / проектная гипотеза: план может быть представлен типизированным графом | Раздельно хранить декомпозицию целей, блокировку задач, поддержку и проверку критерия | Проверить ацикличность декомпозиции и убедиться, что зависимость не подменяет причинное обоснование |
| Предложение Claude / проектная гипотеза: короткое сообщение можно связывать с подробной формой | Двусторонняя проекция текста и структуры с видимыми расхождениями | Проверить, что получатель обнаруживает неоднозначность до принятия обязательства |
| Предложение Claude / проектная гипотеза: глубина детализации может меняться с контекстом | Контекстный профиль выбирает нужные поля и проверки; отсутствующие поля имеют статус | Один сценарий проходит несколько профилей; обязательные требования безопасности нельзя скрыть ускоренным режимом |
| Предложение Claude / проектная гипотеза: краткая передача может работать без модели и сети | ИИ и интернет не обязательны для создания, подтверждения и передачи краткого поручения | Проверить создание, получение, подтверждение и последующую сверку при отключённой сети и ИИ |
| Предложение Claude / проектное решение: ответственное поручение требует человеческого подтверждения | Принятие фиксируется конкретным человеком; роль задаёт функцию и пределы полномочий, но не принимает поручение | Нельзя автоматически превратить предположение модели в назначение, срок, ресурс или критерий приёмки |
| Сравнительная рамка проекта: модель связывает объекты и действия в разных системах | Описывать типы объектов, связи, команды и системы-исполнители, не требуя единого центра данных | Проверить, что отключение адаптера не теряет план и не создаёт фиктивный статус завершения |
| Предложение Claude / проектная гипотеза: личный захват и регулярный обзор можно описывать отдельно | Личный inbox и обзор имеют отдельного владельца и видимость | Проверить, что личная заметка не становится организационным обязательством без решения и принятия человеком |
| Предложение Claude / проектная гипотеза: инцидентный сценарий должен проверять передачу управления | Инцидент, цель реагирования, назначение, журнал и смена руководителя разделены | Сценарий смены руководителя сохраняет время, передающего/принимающего, состояние и нерешённые задачи |

## Ограничения принципов

- Нельзя использовать «кризисный режим» как оправдание отсутствия обязательных мер безопасности или права.
- «ИИ советчик» само по себе не защищает от ошибки: нужны происхождение каждого значения, журнал изменений и человеческое подтверждение обязательств.
- Успешная демонстрация схемы не подтверждает, что она снижает время управления или улучшает результаты.
- Совместимость с Palantir или любой другой платформой не равна независимости от поставщика. Архитектуру и портируемость потребуется испытать отдельно.
